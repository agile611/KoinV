Comprehensive RISC-V Models, Device Trees, and 
Architecture Guide for a Debian-Compatible Linux 
Distribution 
Building a modern, general-purpose Linux distribution for the RISC-V architecture requires 
integrating hardware models, Device Trees (.dts and .dtb), and a resilient system architecture 
rather than relying on a single static package. While the RISC-V Instruction Set Architecture 
(ISA) is free and open, that freedom does not guarantee automatic hardware standardization: 
each manufacturer implements distinct peripherals, clock controllers, memory maps, and 
silicon errata, making the Linux kernel strictly dependent on the Device Tree to boot each 
board. 
Unlike x86_64, a RISC-V distribution faces critical fragmentation across two primary axes: 
1.​ User-space ISA compilation profile: RV64GC (RVA20) for broad compatibility with 
pre-2026 boards versus RVA23 for next-generation hardware featuring mandatory 
vector and hypervisor extensions. 
2.​ Silicon errata and boot variations: Mandatory kernel errata for early SoCs (notably 
T-Head, SiFive, Andes, and StarFive JH7100) alongside firmware and Device Tree 
discrepancies across board revisions. 
To achieve maximum hardware coverage—spanning pre-2026 boards, modern RVA23 systems, 
servers, and constrained embedded devices—the optimal architecture is a 64-bit (riscv64) 
distribution based on Debian 13 ("Trixie") compiled on the RV64GC baseline, enhanced 
with runtime dispatch (glibc-hwcaps + hwprobe + IFUNC), a unified multi-platform kernel 
paired with a modular BSP layer (following the RevyOS model), and a hybrid UEFI-first boot 
stack. 
1. Official Sources and Device Tree Extraction 
Repositories 
A Device Tree source file (.dts) and its shared SoC header files (.dtsi) describe hardware 
topology outside the compiled kernel binary and are compiled via dtc (Device Tree Compiler) 
into the flattened binary format (.dtb or FDT) passed by the bootloader to the Linux kernel. In 
the RISC-V ecosystem, these definitions are distributed across five repository tiers depending 
on their upstreaming status. Note that several older GitHub mirrors 
(devicetree-org/devicetree-source, unmaintained for six years, and riscv-device-tree-doc, 
halted eight years ago) remain purely historical references; builds should prioritize the mainline 
Linux tree, devicetree-rebasing.git, and official U-Boot.

Automated Extraction and Compilation Workflow 
To automate the extraction and compilation of all official Device Trees in a distribution build 
pipeline, follow the standard procedure on the Linux kernel tree: 
1.​ Clone the repository: Run git clone 
[https://github.com/torvalds/linux.git](https://github.com/torvalds/linux.git) --depth=1 (or 
clone the active mirror devicetree-rebasing.git) to inspect definitions. 
2.​ Enumerate mainline boards: List all supported boards by running find 
arch/riscv/boot/dts -name "*.dts" inside the kernel source tree. 
3.​ Register custom or patched .dts files: Ensure every newly added or patched .dts file is 
explicitly listed under dtb-$(CONFIG_...) in the corresponding subdirectory's Makefile; 
otherwise, Kbuild will skip it. 
4.​ Cross-compile kernel and DTBs: Build the kernel image and all .dtb binaries together 
using make ARCH=riscv CROSS_COMPILE=riscv64-linux-gnu- defconfig followed by 
make -j$(nproc) ARCH=riscv CROSS_COMPILE=riscv64-linux-gnu- Image dtbs. 
5.​ Validate against schemas: Verify generated Device Trees against official kernel bindings 
using make dtbs_check to catch deprecated or incompatible properties before 
packaging. 
2. Inventory of DTS/DTB Directories and Files by 
Vendor 
Within the official Linux kernel, arch/riscv/boot/dts/ is organized into vendor subdirectories 
enabled in arch/riscv/boot/dts/Makefile. Between kernel v5.7 and recent patches from 
2025–2026 (including Linux 7.0-rc1 and the November 2026 branch), the structure has 
consolidated eleven major silicon families. While the complete directory layout and primary 
reference files are confirmed across kernel sources, U-Boot, and mailing lists, several recently 
added (andes/, eswin/) or vendor-maintained (renesas/, thead/) directories lack exhaustive 
file-by-file listings in external indexed documentation; running find directly on a full repository 
clone is recommended to capture every file without omission.

3. Complete Catalog of RISC-V Boards and Models by 
Category 
Data from the official RuyiSDK hardware support matrix (updated through September 29, 
2026), combined with mainline Linux kernel definitions and 2026 technical reports, inventories 
94 physical boards in the primary matrix alongside roughly a dozen additional reference 
boards, carrier variants, and platforms documented across upstream repositories and technical 
communities (exceeding 100 physical references), plus over 250 FPGA targets in LiteX-Boards 
and virtual environments. 
To design a coherent distribution, this hardware universe is divided into three tiers based on 
each board's real capability to run a full user-space Linux environment: 
1.​ 54 Application, Desktop, Server, and FPGA Systems capable of running full Linux 
distributions. 
2.​ 18 Ultra-Light, Memory-Constrained (64 MB–512 MB), or Hybrid ARM+RISC-V 
Boards requiring minimal root filesystems. 
3.​ 27 Microcontroller (MCU) and RTOS-Only Boards recommended for exclusion from a 
general-purpose Linux distribution. 
3.1. Application Boards, SBCs, Laptops, Workstations, and FPGAs (Full 
Linux) 
This tier groups 49 boards from the RuyiSDK matrix along with 4 additional models and the 
Renesas RZ/Five platform (54 entries total). Characterized by 64-bit architectures and 512 MB 
to 64 GB of RAM (or DDR4 slots), they support full distributions such as Debian, Ubuntu, 
Fedora, Arch, Gentoo, NixOS, openEuler, or RevyOS. Pre-2026 platforms operate on RV64GC / 
RVA20 profiles, whereas SpacemiT K3-based systems implement the RVA23 profile.

A standard Debian or Ubuntu image built on glibc and systemd with graphical workloads 
typically exceeds 500 MB of rootfs and will struggle severely on 64 MB systems, whereas 
minimal images built with musl and BusyBox (such as Alpine Linux or Buildroot) occupy 5 MB to 
50 MB. To support this tier without bloating the primary desktop/server distribution, offer a 
separate minimal image variant (without systemd, built via Buildroot/BusyBox or heavily 
stripped packages) that shares the exact same kernel and .dtb files.

3.3. Microcontrollers and RTOS Boards (Recommended Exclusion) 
The RuyiSDK hardware matrix also tracks 27 microcontroller (MCU) boards or tiny SoCs with 
minimal SRAM (2 KB to 1 MB SRAM, or up to 16–32 MB PSRAM on larger models). Because 
standard Linux environments require a CPU with an MMU and DRAM (at least 8–32 MB even in 
minimal LiteX builds), and these 27 boards only record tests with Real-Time Operating Systems 
(RT-Thread, FreeRTOS, Zephyr, LiteOS, ThreadX, or uCOSII), they should be excluded from a 
general-purpose Linux distribution: 
●​ WCH QingKe Family (10 boards): CH32V003-EVT (2 KB SRAM), CH32V103-EVT (20 KB), 
CH32V203-EVT (20 KB), CH32V208-EVT (64 KB), CH32V303-EVT (64 KB), 
CH32V305-EVT (32 KB), CH32V307-EVT (64 KB), CH573F-EVT (18 KB), CH582F-EVT (32 
KB), and CH592X-EVT (26 KB). 
●​ Espressif ESP32 Family (6 boards): ESP32-C2 (272 KB SRAM), LUATOS ESP32-C3 and 
TTGO T-OI-Plus (400 KB SRAM, RV32IMC), ESP32-C6 (512+16 KB SRAM, RV32IMAC), 
ESP32-H2 (320 KB SRAM, RV32IMAC), and ESP32-P4 (16/32 MB PSRAM, tested with 
FreeRTOS). 
●​ GigaDevice GD32VF103 Family (4 boards, Nuclei Bumblebee, 32 KB SRAM): Longan 
Nano, Nuclei DDR200T, RV-STAR, and TTGO T-Display-GD32. 
●​ Bouffalo Lab MCU Family (4 boards): Pine64 Pinecone (BL602, SiFive E24, 276 KB), 
Sipeed M0 sense (BL702, SiFive E24, 132 KB), Sipeed M0P Dock (BL618, XuanTie E907, 480

D133EBS (XuanTie E907, 1 MB SRAM + 8 MB PSRAM), and R128-EVT (XuanTie C906, 1 MB 
SRAM + 16 MB PSRAM).

5. Architectural Blueprint for a Debian-Compatible 
RISC-V Distribution 
Having every .dts and .dtb only solves hardware description for the kernel. To boot reliably 
across all target hardware while remaining clean, modern, and binary-compatible with Debian, 
the distribution should be engineered around four architectural pillars: 
5.1. CPU Architecture & User Space: riscv64 (RV64GC) + glibc-hwcaps 
●​ 64-bit Exclusive (riscv64): Target the official 64-bit little-endian riscv64 architecture, 
fully supported in Debian since Debian 13 ("Trixie") and easily bootstrapped via 
mmdebstrap or debootstrap. riscv32 is not an official Debian release architecture, and 
nearly all 32-bit RISC-V silicon consists of memory-constrained MCUs unsuitable for a full 
Linux user space. 
●​ RV64GC (RVA20) Baseline for Broadest Compatibility: While Ubuntu 25.10 and 26.04 
LTS ("Resolute Raccoon") raised their mandatory minimum baseline to RVA23 (RVA23U64), 
binaries compiled for RVA23 will not execute on pre-2026 boards limited to RV64GC or 
RVA20 (such as VisionFive 2, Milk-V Mars, Star64, Lichee Pi 4A, Allwinner D1, or Milk-V 
Pioneer). Following Debian 13 ("Trixie")—and noting that even Debian 14 ("Forky") is 
expected to raise its baseline at most to RVA20U64 (adding Zicntr and Zicsr)—by 
compiling the base user space on RV64GC ensures full compatibility with official Debian 
repositories and existing hardware. 
●​ Modern Acceleration Without Breaking Compatibility (glibc-hwcaps + hwprobe + 
IFUNC): Rather than splitting the distribution into incompatible repositories or sacrificing 
performance on RVA23 silicon (like SpacemiT K3), leverage runtime dispatch: 
○​ Use glibc-hwcaps backed by the Linux hwprobe syscall (which exposes real 
hardware capabilities, including the RVA23U64 profile, to user space) to 
dynamically load optimized builds of performance-critical shared libraries (openssl, 
libgcrypt, libjpeg-turbo) only when supported by the host CPU. 
○​ Leverage IFUNC runtime resolvers in glibc (querying 
RISCV_HWPROBE_KEY_IMA_EXT_0) to select vectorized RVV 1.0 routines on the fly 
within a single base binary. 
○​ (Optional) Maintain a secondary opt-in repository or overlay compiled with 
rva23_defconfig / -march=rva23u64 only for workloads requiring whole-system 
RVA23 optimization. 
5.2. Linux Kernel Strategy: Unified Mainline Kernel + Modular BSP 
Layer 
●​ Unified Mainline Kernel with Mandatory Errata: Several commercial RISC-V chips were 
designed prior to the ratification of standard extensions such as Zicbom (cache-block 
management) or Svpbmt (page-based memory types) and will hang or suffer DMA 
failures on a pure unpatched kernel. The primary kernel image (linux-image-riscv64) must 
compile all available .dtb files and keep four critical errata families enabled in 
arch/riscv/Kconfig.errata:

●​ Modular BSP Layer (RevyOS Model): A major challenge for pure Debian on RISC-V is 
the lag between a board's commercial release and full upstreaming of vendor 
subsystems (GPU, NPU, video codecs, USB). Adopting the RevyOS architecture solves 
this cleanly: preserve a 100% standard Debian (trixie) user space and APT ecosystem 
while offering modular, SoC-specific kernel and firmware packages (e.g., for TH1520 or 
SG2042) alongside the mainline kernel. 
●​ Flexible MMU Paging (Sv39 / Sv48 / Sv57): The Linux kernel supports 3-, 4-, and 5-level 
paging and automatically selects the widest mode accepted by the hardware's satp 
register (Sv57, providing a 57-bit / 128 PB virtual address space, on modern chips and 
QEMU). Because certain older user-space runtimes or emulators can encounter issues 
with 57-bit virtual addresses, compile the kernel with full Sv57 support while 
documenting and exposing no5lvl (forces Sv48) and no4lvl (forces Sv39) kernel 
command-line parameters as boot fallbacks. 
5.3. Boot Chain, DTB Variations, and UEFI/ACPI Transition 
Modern RISC-V hardware follows a strict privilege-level boot sequence: the silicon's BootROM 
(ZSBL) in Machine Mode (M-Mode) loads U-Boot SPL (FSBL) to initialize DDR RAM; SPL then 
loads a FIT container holding OpenSBI (compiled with PLATFORM=generic so a single binary 
works across multiple boards) and U-Boot in Supervisor Mode (S-Mode), which hands control 
over to the Linux kernel alongside the .dtb. 
Even within the same board model, Device Trees exhibit critical variations that boot scripts or 
overlays must handle: 
●​ Memory node overrides: In official U-Boot v2026.04, jh7110-common.dtsi defaults to 
declaring 4 GiB at memory@40000000, requiring an adjustment on 8 GiB VisionFive 2 
boards so both EFI and Linux detect the full 8 GiB. 
●​ PCB revision differences: Between VisionFive 2 PCB revisions (v1.2B and v1.3A), 
microSD card detection varies between cd-gpios on GPIO 41 and the broken-cd 
property used in related JH7100/JH7110 files, causing regressions across kernels 6.10 
through 6.15. 
●​ Disabled buses and PMIC variants: On the Microchip PolarFire Video Kit, i2c0 and i2c1 
exist in the .dts but remain disabled until explicitly set to status = "okay". Similarly, 
industrial SpacemiT K3 CoM260 TQ modules combine two power-regulator variants 
where the bootloader configures voltages before booting Linux and describes 
differences via compile-time Device Tree overlays. 
To avoid maintaining dozens of rigid, board-specific disk images, structure the boot stack 
around a UEFI-first standard with a non-UEFI fallback: 
●​ Primary Path (UEFI-First + EBBR/BRS): 
○​ Firmware & Bootloader: Pair generic OpenSBI (PLATFORM=generic) with modern 
U-Boot (OF_UPSTREAM) exposing UEFI services to load 
EFI/BOOT/BOOTRISCV64.EFI. In Debian Trixie, both systemd-boot 
(systemd-boot-efi, ideal for streamlined Unified Kernel Images / UKIs) and 
grub-efi-riscv64 (best for update-grub and classic Debian installer workflows) are 
officially packaged for riscv64. 
○​ Transparent DTB Updates (u-boot-efi-dtb): Include Debian Trixie's 
u-boot-efi-dtb package so that even when a board boots from an older factory 
U-Boot flashed in SPI NOR, the UEFI loader reads updated .dtb files from /boot 
rather than relying on stale firmware Device Trees (retaining the option to pass 
$fdt_addr_r explicitly to bootefi for early vendor BSP quirks such as initial SpacemiT 
K3 U-Boot builds). 
○​ Server Readiness (BRS / ACPI): Keep ACPI enabled alongside Device Tree in the 
kernel so the same image boots standardized RVA23 servers compliant with the 
RISC-V Server Platform Specification (BRS) without requiring board-specific .dtb 
files. 
●​ Fallback Path (Non-UEFI Vendor U-Boot): 
○​ Package u-boot-menu (which auto-generates extlinux.conf boot menus on every 
kernel install/upgrade) and flash-kernel to support boards shipping with 
stripped-down vendor U-Boot builds lacking UEFI.
